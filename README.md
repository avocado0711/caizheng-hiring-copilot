# 才证 招聘决策台

一个本地优先、模型可替换的多 Agent 招聘研究工作台，支持岗位评价、简历筛选、公开信息 RAG、经历证据卡和面试追问。

它不会把录用决定交给大模型。系统先由 HR 锁定岗位评价卡，再逐份生成带原文行号的证据卡，最后用确定性规则完成计分和排序。

## 已实现功能

- 岗位评价卡：岗位描述、评价项、证据关键词、权重、硬性条件
- 从 JD 生成评价项建议，保存前可人工修改
- 可选 LLM 驱动四个职责独立的筛选 Agent
- 评价卡 Agent、结构化 Agent、证据匹配 Agent、证据审计 Agent 和摘要 Agent 分工执行
- 本地公开信息知识库与中文 BM25 检索
- 公司、团队、学校、论文和专利实体抽取
- 带来源引用的经历含金量证据卡
- 根据证据缺口生成面试追问
- 模型原文引用逐字校验，无法核验的结论自动回退
- 一次批量导入最多 100 份简历
- 支持 TXT、Markdown、JSON、DOCX、PDF 和常见图片
- 提取姓名、邮箱、电话、工作年限、学历、简介和技能区
- 每个评价项保留原文摘录、行号、命中关键词和置信度
- 点击候选人姓名可打开逐行简历原文预览，支持搜索高亮与复制
- “未提及”与“明确不具备”分开表示
- 邮箱、电话、正文哈希重复检测
- 硬性条件闸门、权重匹配分、候选人横向证据矩阵
- HR 可覆盖评价等级、填写备注、设置短名单/待讨论/不通过
- 追加式决策审计历史：记录审核人、时间、修改前后状态与评价覆盖
- 浏览器内 AI 电话初筛：基于证据缺口提问、语音转写、文字兜底和通话报告
- CSV 导出
- 数据只保存在本机

## 启动

Windows 下双击 `启动招聘筛选.bat`，程序会启动本地服务、优先使用 Microsoft Edge 打开，并准备手机扫码接听演示通道。

首次在干净目录演示，或需要恢复到标准比赛场景时，直接双击 `准备并启动演示.bat`。它会先生成演示数据，再启动服务。

`准备并启动演示.bat` 使用专用全新演示模式：每次运行都会恢复标准演示数据、强制播放品牌开场动画和完整教程，并重新生成手机接听二维码。即使 Edge 之前已完成引导，也会按第一次访问展示。

也可以在项目目录运行：

```powershell
node server.js --open
```

强制使用 Microsoft Edge：

```powershell
node server.js --open-edge
```

启用手机扫码接听与 Cloudflare 临时 HTTPS 隧道：

```powershell
node server.js --open-edge --phone-demo
```

默认地址为 `http://127.0.0.1:3030`。端口被占用时会自动尝试后续端口。

同一数据目录只允许一个才证服务进程写入。再次启动时会打开已有服务，避免多个实例互相覆盖 `state.json`。

## 使用流程

1. 在“岗位评价卡”填写岗位名称和 JD。
2. 生成或手动配置评价项，确认关键词、权重与硬性条件后保存。
3. 在“批量导入”拖入简历，等待生成证据卡。
4. 在“比较与排序”查看排序表或证据矩阵。
5. 点击候选人检查原文证据，必要时覆盖等级并标记审核状态。
6. 可在“AI 电话初筛”中选择候选人，在浏览器内完成语音问答。
7. 导出 CSV 进行后续流程。

## 网页 AI 初筛

网页初筛使用浏览器语音合成朗读问题，并使用浏览器语音识别获取候选人回答。若浏览器不支持语音识别，可以直接输入或修改转写内容。

通话开始前必须确认候选人已被告知 AI 身份、语音识别和转写用途。系统会先询问是否同意继续，再进入岗位问题。

本应用只接收并保存转写文字，不接收或保存音频文件。浏览器语音识别是否在本地或云端处理取决于浏览器和系统配置，不代表音频一定留在本机。

问题来自候选人的简历证据缺口、薄弱评价项和带来源的公开资料，结束后生成客观回答摘要并写入候选人审计历史。AI 不会自动修改审核状态或作出录用决定。

## Agent 架构

LLM 只是底层能力接口。四个筛选 Agent 分别存放在 `agents/` 下的独立目录中，通过统一的 `completeJson()` 接口调用兼容模型；评价卡生成是独立工作流，不属于候选人筛选流水线。

1. **评价卡 Agent**：从 JD 生成岗位相关评价项，HR 确认后锁定。
2. **简历结构化 Agent**：提取职位、年限、学历、工作时间、地点和技能。
3. **岗位证据匹配 Agent**：逐项判断强/中/弱/未提及，并提供逐字原文。
4. **证据审计 Agent**：校验原文、硬性条件、低置信度、信息缺口和字段冲突。
5. **候选人摘要 Agent**：只能使用已审计证据生成摘要，不参与评分或排序。

计分、硬性闸门、排序和导出由确定性代码完成。模型或供应商变化不会改变这些业务规则。

Agent 与知识能力目录结构：

```text
agents/
  简历结构化Agent/
  岗位证据匹配Agent/
  证据审计Agent/
  候选人摘要Agent/
  orchestrator.js
knowledge/
  demo/
  retriever.js
  entity-extractor.js
  value-assessment.js
  interview-questions.js
workflows/
  岗位评价卡生成.js
```

`knowledge/demo/星桥智能科技.json` 是为比赛准备的完全虚构企业知识包，与任何现实企业、学校或个人无关。

## 评分规则

每个评价项根据命中关键词数量得到“强 / 中 / 弱 / 未提及”四档：

```text
匹配分 = Σ(评价项权重 × 等级分值) / Σ评价项权重 × 100
```

等级分值为强 `1`、中 `2/3`、弱 `1/3`、未提及 `0`。硬性条件单独形成闸门，存在硬性缺口的人排在已覆盖者之后。

模型可用时优先采用通过原文审计的证据等级；模型未配置、部分 Agent 失败或评价卡变化时，自动回退到透明、可重复的关键词基线。关键词只能说明“简历中出现了相关证据”，不能替代 HR 对证据质量的判断。

## 文件解析说明

- TXT、Markdown：直接读取。
- DOCX：读取 `word/document.xml`，不执行文档宏。
- PDF：优先解析 PDF 对象和文字流，并支持使用 `ToUnicode` 映射恢复常见中文 CID 字体。原生文字不可用时，自动用本地 PDFium 按 220 DPI 渲染，再逐页调用 Windows OCR；加密或损坏 PDF 会明确报错。
- 图片：默认调用本地 RapidOCR；不可用时自动降级到 Windows OCR。识别前会自动纠正 EXIF 方向，并对较小图片进行高质量放大。
- OCR 结果会生成质量分；低质量结果会在候选人详情中标记“需复核”，并提示核对姓名、技能和关键经历。

设置 `HIREPROOF_OCR_ENGINE=windows` 可强制使用 Windows OCR；默认值为 `rapidocr`。
- 旧版 `.doc` 暂不支持，请另存为 `.docx`。

## 公开信息与 RAG

知识库页面支持查看、添加、删除和检索本地知识资料。检索结果会返回标题、实体、来源说明、发布日期、虚构数据标记和置信度。

内置演示知识库包含 144 份公开知识资料和 17 份简历聚合资料，覆盖虚构企业、研发团队、技术架构、岗位标准、论文、专利、高校专业及招聘方法；可用 `npm.cmd run knowledge:build-demo` 重新生成。

岗位评价项生成会把检索到的知识片段作为上下文，并返回实际使用的来源 ID。候选人分析会抽取公司、团队、学校、论文和专利实体，再检索知识库形成“经历含金量证据卡”。

公开资料支持发布机构、来源 URL、发布时间、抓取时间、授权许可和来源包批量导入。示例结构见 `knowledge/public-sources.example.json`。

实体抽取会区分公司、组织、学校、团队、岗位和论文/专利等类型，不会把岗位名称或技能标签直接当作公司。知识关联会按候选人的公司和学校实体做边界过滤：其他公司的技术资料、年报和论文不会被当作候选人的背景佐证；岗位标准和简历样本聚合只作为岗位模式参考。界面展示“知识库命中 X 条”，不把这组命中数量解释为公开资料真实性、个人价值或录用结论。

### 100 份合成简历知识包

项目把 `简历筛选/` 中的 100 份合成 PDF 转换成招聘证据知识：

- 1 份全量岗位与技能总览。
- 16 个岗位方向的聚合知识文档。
- 覆盖全部 100 份简历样本。
- 每份样本保留脱敏职责、项目、技能、量化成果和脱敏原文。
- 不把姓名、邮箱、电话和受保护属性写入全局知识库。

生成或更新知识包：

```powershell
npm.cmd run knowledge:build-resumes -- --source "D:\26572\简历筛选"
```

知识包保存为 `knowledge/demo/resume-screening-knowledge.json`，启动应用和重置演示数据时会自动合并。

该指标只描述岗位相关证据的完整度和可验证程度，不代表个人价值或录用结论。学校、公司和论文只有与岗位任务相关时才作为辅助证据。

## 项目 Embedding 模型

项目已使用本机 BGE-M3 训练 LoRA 领域适配模型，并建立了 904 份合成知识片段的向量索引。

- 模型：`models/hireproof-embedding-lora-v4`
- 索引：`embedding_index/`
- 训练报告：`ml/TRAINING_REPORT.md`
- 复现说明：`ml/README.md`

提交目录只保留约 1 MB 的最终 LoRA adapter，不包含 BGE-M3 底座和中间 checkpoint。首次使用请安装 `ml/requirements.txt`，或通过 `HIREPROOF_BASE_MODEL` 指向本地底座。应用会自动探测项目 `.venv`、用户目录下的 Python 3.x 和系统 Python；仍无法发现时，在 `.env` 中用 `HIREPROOF_PYTHON` 指向 `python.exe` 的完整路径。`npm.cmd run preflight` 会显示实际使用的解释器并检查向量依赖。

正式索引使用 50% 基础 BGE-M3 与 50% LoRA 向量融合。最终检索使用 BM25 + Dense + RRF Top 30，并将 Reranker 作为权重 1.0 的辅助排序信号。

应用启动时会自动拉起 `ml/embedding_service.py` 本地模型服务。模型加载期间知识搜索自动使用 BM25；加载完成后默认切换为：

```text
BM25 + LoRA 向量 + RRF
```

知识库页面勾选“深度检索”后才会启用 BGE Reranker。Reranker 采用懒加载，默认不占用额外显存。

通过界面新增知识资料时，会同步生成并保存该资料的向量。设置 `HIREPROOF_DISABLE_VECTOR_SERVICE=1` 可以完全关闭本地向量服务。

最终留出检索结果：

- BM25 Recall@5：0.552
- 混合 RRF Recall@5：0.557
- 可选深度检索 RRF + Reranker Recall@5：0.557
- 可选深度检索 RRF + Reranker MRR：0.370

## 数据与隐私

默认数据文件为 `data/state.json`，包含简历提取文字、解析结果和人工审核记录。原始上传文件不落盘，图片 OCR 临时文件在识别完成后删除。

模型服务通过本机 `.env` 的 `LLM_API_KEY`、`LLM_BASE_URL` 和 `LLM_MODEL` 配置，只在服务端使用，不会返回浏览器。密钥文件已加入 `.gitignore`。该接口面向 OpenAI-compatible Chat Completions 服务，具体供应商属于部署配置，不属于项目业务代码。

启用模型 Agent 后，简历文字会发送到 `LLM_BASE_URL` 指向的服务。发送前会去除姓名、邮箱、电话、证件号，以及年龄、性别、婚育、民族、籍贯、住址等保护字段；发送内容仍属于招聘个人信息，应按企业数据政策评估是否允许使用外部 API。将 `HIREPROOF_AI_ENABLED=false` 可完全关闭外部分析并只使用本地关键词基线。

- 服务只监听 `127.0.0.1`；未启用模型 Agent 时简历不会发送到外部网络。
- 上传单文件限制为 15 MB，前端按 45 MB 自动拆批，服务端单次请求简历总量限制为 60 MB。
- 真实招聘材料应限定访问人员，并设置明确的数据保留期限。
- 不要将年龄、性别、婚育、籍贯、照片等与岗位无关的信息加入评价项。
- `data/` 已被 `.gitignore` 排除，仍应在备份和终端录屏时注意简历隐私。

生成比赛或交付压缩包时不要直接压缩整个项目目录。运行：

```powershell
npm.cmd run package:submission
```

脚本会排除 `.env`、`.env.*`、`data/`、备份、缓存和运行目录，并在压缩前再次检查暂存内容。生成的 ZIP 位于 `dist/`。

## 后续扩展
